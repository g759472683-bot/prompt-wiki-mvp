- 每张卡都有 1–3 条引用；所有页面为 `status: draft`、单来源 `yellow`。

## 这轮修掉的问题

1. **L1 超 12 字导致整张卡被丢**：增加"从 L2 提取短关键词"的兜底，pitch 从 2 张恢复到 12 张。
2. **L2 超 28 字导致整张卡被丢**：超长句按逗号/分号拆成 ≤28 字的骨架，再校验 3–5 条。
3. **`do_not_say` 被模型写成"绝对化表述"**：prompt 明确要求写实际禁说短语；无则空数组。
4. **YAML 锚点污染**：`evidence_refs` 在页面和 card 里复用同一列表，PyYAML 生成 `&id001/*id001`；改为复制列表。
5. **fallback 复述 L2**：要求以"具体细节我按原话/复盘确认"开头，再给一个确定事实。

## 仍然存在的问题

- **同步链路太慢**：42–93s/份（两次 LLM 调用），必须上 job/worker。
- **只有 claim/metric/qa**：`story`/`entity` 未生成；行为面试的 STAR 结构还不够。
- **没有审核/发布**：卡只在 `.staging/`，未经过人工批准，不能给 App。
- **跨文档不合并**：同一断言来自简历和复盘时会生成两页；D5 需要去重/合并。
- **单来源全黄**：需要第二份材料交叉验证才能变绿；这符合契约，但内测前要补文档。
- **pitch 类材料仍偏弱**：公司级数字多、个人动作少，卡片质量低于简历/复盘；需要场景模板。

## 对下一步的含义

1. D5 先做 **jobs + 审核台**，否则 70s 同步请求和"直接进 staging"都不能产品化。
2. `story` 页优先于 `entity`：面试的"最大失败/最难项目"需要 STAR，不该只靠 claim。
3. 场景 `prep` 应把"文档编译"与"20 张卡"分开：一份文档的卡可以复用到多场对话。
4. 5 份文档的 token 成本约 8k–19k output/份；按内测规模可接受，但需要预算上限与缓存。
